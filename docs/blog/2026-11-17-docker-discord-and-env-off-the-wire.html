1. Colima, PostgreSQL 17 and app ports (#69)

Your Windows workstation should be able to run docker ps, docker compose, Testcontainers and psql against the Apple Silicon MacBook without installing Docker Desktop on Windows or opening unauthenticated TCP 2375 or 5432 on Wi-Fi. The spec in specs/m1-cloud-services (tracked in #70) plans a second, workload-only SSH tunnel alongside the dashboard tunnel (<user> and <port> below are placeholders for your Mac username and registered container or dev-server port):

specs/m1-cloud-servicesplanned bridge
windows 127.0.0.1                           otto-mac 127.0.0.1 (loopback only)
-----------------------------------------   ----------------------------------------------
127.0.0.1:23750  -- ssh -N -F none -------→ /Users/<user>/.colima/default/docker.sock
127.0.0.1:5432   -- services-tunnel.json -→ 127.0.0.1:5432 (postgresql@17)
127.0.0.1:<port> -------------------------→ 127.0.0.1:<port> (containers & dev servers)
  • Sized for unified memory. Colima starts with Apple's vz hypervisor and virtiofs capped at 4 CPUs and 4 GiB RAM on 16 GiB Macs (2 CPUs and 2 GiB on 8 GiB Macs), coordinated with the thermal and RAM arbiter in src/arbiter.rs so parallel builds do not push a fanless Air into swap thrashing.
  • Unix socket forward, no sshd PATH trap. OpenSSH forwards workstation 127.0.0.1:23750 straight to Colima's Unix socket on the Mac and configures a docker context named otto-mac, avoiding docker system dial-stdio failures under minimal non-interactive sshd environments.
  • Decoupled from the dashboard tunnel. Desired forwards live in .cheap-otto/services.json and their tunnel in .cheap-otto/services-tunnel.json, validated disjoint from DashboardSet::ports() (7420, 7421, 7430). Adding or removing port 3000 restarts only the services tunnel; Mission Control and the Reviewer never blink.
  • Loopback-verified Postgres and cached UI state. Startup checks SHOW listen_addresses, rewrites and restarts postgresql@17 if needed, and fails closed if a non-loopback listener remains. Mission Control's planned GET /api/services reads cached files written atomically under services.lock and never spawns SSH on page load.

2. @Claude and @Agy on Discord (#71)

Driving claude and agy today needs an SSH session or a workstation tunnel. specs/m1-chat-control (#71) lets you talk to both agents independently from Discord on your phone or browser for free, with zero inbound ports on the Mac, zero third-party npm packages and zero new Cargo dependencies:

  • Stdlib Node 24 sidecar, pure Rust core. A small launchd service (com.cheapotto.chat.discord) keeps outbound Discord Gateway v10 WebSockets open using Node 24's built-in WebSocket and fetch, prefilters allowed_user_ids so unauthorized users spawn nothing, and passes allowlisted events to pure Rust (src/chat.rs).
  • Multi-account repo hub. Clones live under ~/repos/<gh-account>/<repo> (<gh-account> and <repo> are placeholders) with per-account .gitconfig includeIf rules and a broker-only credential helper, so personal and org repositories never mix GitHub tokens or commit authors.
  • One thread, one shared worktree, two memories. Posting in a mapped #<repo> channel creates a Discord thread and a dedicated worktree (~/repos/<gh-account>/.worktrees/<repo>--<slug>, where <slug> is a placeholder) storing both claude_session_id and agy_conversation_id. Per-worktree queue tickets serialize turns inside one thread while separate threads run in parallel (up to 3 across the Mac by default).
  • Separate macOS user for agent turns. During spec review on #71, Cubic pointed out that stripping GH_TOKEN and DISCORD_*_TOKEN from child environment variables does not stop a same-UID agent from reading ~/.cheap-otto/tokens/ or .git/config. The spec runs agent turns under a separate macOS user that can write only the working tree (with safe.directory configured for read-only git inspection), while the operator-owned broker runs git add, git commit, git push and gh with an empty core.hooksPath.

3. Next up: .env off the wire and away from agents

Today .gitignore and CI's PR Governance & Secret Guard block .env and .env.* (except .env.example) from git, so cheap-otto sync rightly leaves your local .env behind on Windows. Once containers, migrations, dev servers and chat-driven worktrees run on the Mac, those workloads still need runtime secrets — and both shortcuts people reach for break security:

  • Never on the wire to the Mac. Copying raw .env files or passing KEY=VALUE pairs from Windows over SSH argv, dry-run plans, history.jsonl or Mission Control HTTP bodies puts plaintext secrets into command histories, logs or network payloads. The next spec keeps secret values off the Windows-to-Mac wire altogether: secrets are provisioned, unlocked or pulled directly on the Mac into operator-owned 0600 storage, while the bridge exchanges only .env.example schemas, variable names and missing-key diagnostics.
  • Never through an agent. Pasting a .env into a task prompt or leaving a readable .env inside an agent worktree ships live API keys and database URLs straight to external model APIs and session logs. Coding agents (claude, agy, kiro) and Code Tender will see only .env.example key names; the operator-owned broker injects real .env variables strictly into the target app, test, migration or container process at runtime, behind the same separate-UID wall designed in #71.
